# 安全基座

随芯调会调整 Windows 电源方案和进程优先级。只要涉及系统状态修改，就必须满足三个条件：可回滚、可解释、受保护。

这份文档描述当前调度与配置恢复基座。现有系统写入覆盖电源方案、最大处理器状态百分比、进程策略、NVIDIA 官方 NVML GPU 锁频保护及硬件电源瞬态急停防护（Power Emergency Gate）。

## 原则

- 先捕获状态，再修改状态。
- 同时记录原值和本次事务最后应用值，恢复前必须读取当前值对账。
- 回滚状态必须可靠、原子地写入磁盘。
- 部分回滚失败时，不能丢弃未恢复项目。
- 不把进程提升到 `RealTime` 优先级。
- 不调整受保护的 Windows 关键进程，也不调整调度器自身；该保护同时覆盖优先级和 Efficiency Mode 写入。
- 调度决策留在 Core，平台动作留在 Infrastructure。

## 调度事务

当某个 Profile 命中当前前台应用时，调度器按以下顺序执行：

1. 检测能力、前台应用、当前供电状态和当前电源方案，加载本地配置及兼容机型策略包。
2. 匹配已启用 Profile，判断是否需要切换会话；变化时先恢复旧事务，未完成的恢复阻止新写入。
3. 准备受影响进程的身份、原优先级和所需效率模式状态。
4. 在切换电源方案或修改进程之前，持久化第一份回滚基线。
5. 切换电源方案并读回确认；在已确认的目标方案及明确供电分支上读取高级电源项原值，再把这些基线合并到同一事务并持久化。
6. 应用高级电源项、前台优先级和后台策略，每项修改必须读回确认。
7. 收集运行信息并持久化 SQLite 调度审计；失败时恢复已应用状态并暂停调度。
8. 审计成功后登记内存活动会话，供后续检测和恢复使用。

如果 `powercfg` 或某个硬件 Provider 不可用，能力检测只将对应能力标记为不支持，不阻断其他只读能力的检测；用户主动取消仍按取消处理，不会被伪装成“不支持”。

每项进程能力独立降级：不支持优先级调整时，不阻断设备仍支持的 Efficiency Mode；不支持回滚时，优先级和 Efficiency Mode 等写入动作统一阻止。若设备声明支持 Efficiency Mode，但某个目标进程无法读取当前状态，则该进程动作按未知状态失败，不得伪报成功；只有明确不支持该能力时才过滤对应动作。

每次检测使用独立 `RunId`，一次实际配置会话使用稳定的 `TransactionId`。同一 Profile、进程和供电状态持续生效时沿用事务 ID；切换会话时先结束并恢复旧事务，再创建新事务。不同事务的回滚状态禁止合并。

新的危险动作不应绕过这条事务路径。

## 回滚状态

回滚状态先写入临时文件，再移动到目标路径。这样可以避免进程在写入中途退出时留下半截 JSON。

执行回滚时，每个项目独立恢复：

- 只有当前值仍等于随芯调最后应用值时，才写回原值。
- 如果用户或其他软件后来修改了该值，随芯调跳过写回并尊重当前设置。
- 无法读取当前值时保留回滚项，不猜测、不强制覆盖。
- 电源方案写入返回成功后必须再次读取并确认目标方案；无法确认时按失败处理，不继续信任后续依赖该方案的动作。
- 高级电源参数写入返回成功后同样必须读取并比对目标值；无法确认时按失败处理并交给事务回滚。
- 电源方案或高级参数回滚返回成功后也必须再次读取并比对原值；读回不一致时保留待回滚状态，不能删除状态文件或伪报恢复完成。
- 旧版回滚数据如果缺少应用值，只清理对应旧项目，不执行不安全恢复。
- 恢复成功的项目会从待回滚状态中移除。
- 恢复失败的项目会保留，供后续重试。
- 只有全部待恢复项目已恢复，或按当前值、进程身份及旧记录规则安全跳过，不再有待处理项后，回滚文件才会删除。
- 回滚状态文件存在但损坏、无权限或暂时不可读时，不得把它当成“没有状态”；原文件保持不动，新的系统写入必须阻止，并在状态中心和日志中提示处理。
- 回滚状态即使能被 JSON 解析，也必须通过结构校验：集合不能为 `null`，进程 ID、进程身份、优先级、供电模式和处理器限制必须在安全范围内，`applied` 条目必须对应同一进程的 `original` 条目；校验失败时原文件保持保护，不得进入 Provider 写入路径。
- 高级电源策略只有在供电来源明确为交流电或电池时才允许读写；来源为 `Any`/未知时不猜测 AC 或 DC，避免把错误的供电分支写入电源方案。
- 启动自动回滚本身失败时，应用不会继续自动调度，而是保留暂停状态并在状态中心和日志中明确提示。
- 启动会话元数据损坏或不可读时，应用按未知安全状态处理，强制暂停自动调度，并在可行时继续尝试回滚已记录的系统状态。
- 即使启动会话标记缺失，只要仍存在待回滚状态，启动流程也会先尝试恢复；恢复未完成前不得开始新的自动调度。
- 如果用户关闭启动自动回滚，但磁盘上仍有待恢复状态，应用不会绕过它继续写入，而是保持暂停并要求用户手动处理。
- 启动会话元数据不可读时，不得用新的活动会话标记覆盖原文件；原文件保持保护，后续启动继续按未知安全状态暂停，直到用户修复或移除该文件。
- 启动失败计数损坏或不可读时，不得把历史重置为空或覆盖原文件；安全保护会暂停自动调度，并要求先处理该运行元数据。
- 正常退出时如果启动失败计数无法读取或存在大小写歧义，也不得把会话标记为干净；下次启动必须继续进入保护流程。
- 调度运行中如果启动会话文件变得不可读，应用不会继续写入新的会话元数据，而是暂停调度并尝试恢复刚刚应用的会话。
- 调度动作已经写入但启动会话元数据无法保存时，同样必须立即暂停调度并用独立令牌尝试回滚；不能只停止监控而留下已应用的系统状态。
- 启动保护状态不可读或回滚仍未解决时，恢复按钮不能绕过安全闸门；成功手动回滚只解除待回滚项，保护状态损坏仍需修复后重新启动应用。
- 前台窗口暂时消失或进程检查失败时，如果存在活动调度会话，调度器会先用独立令牌恢复旧会话；恢复失败会保留阻断状态，不能把焦点丢失当成正常无匹配而继续留下系统修改。
- Profile 连续异常退出达到禁用阈值但配置存储无法写入时，必须强制暂停自动调度并保持恢复入口锁定；不能因为“异常后暂停调度”选项关闭就继续应用无法禁用的 Profile，只有修复存储并完成人工确认后才能恢复。
- UI 设置文件损坏、为空或路径类型错误时只使用安全默认值，不自动覆盖原文件，并通过配置加载问题提示用户处理；成功保存新设置后才清除该提示。
- 手动回滚和正常退出回滚都会读取回滚文件进行二次确认；仍有残留时显示未完成，不清除待回滚状态，也不把启动会话标记为正常关闭。
- 同一个 `FileRollbackManager` 实例会串行执行状态捕获、读取和回滚，避免并发 Capture 丢失待恢复项目，或并发 Rollback 重复写入系统状态。
- 自动监控的启动、停止和手动回滚共享生命周期闸门；停止时会先停止焦点事件入口，并等待周期循环、焦点刷新和正在进行的评估收敛后再释放监控任务。
- 动作执行器在部分写入后抛出异常、返回失败或收到取消时，调度器会使用独立取消令牌尝试即时回滚，避免调用方取消直接跳过恢复。
- 指标采集或结果整理阶段收到取消时，活动会话会在登记前先执行独立令牌回滚，避免“动作已写入但会话尚未可追踪”的窗口。
- 新会话首次写入运行审计必须先于内存活动会话登记；如果 SQLite 记录失败，已应用的动作会用独立令牌回滚，并暂停后续自动调度，避免“系统已修改但运行状态未知”。
- 文件日志不可用时保留内存诊断记录，日志写入失败不得反向阻断启动、调度或回滚流程。
- 能力检测缓存支持失效代次；刷新或设备切换发生在检测进行中时，已过期的检测结果不会重新写回缓存，下一次读取会重新检测。
- 设置绑定写入失败时会回退内存中的新值，并将失败记录到日志与状态中心；启动项注册表和设置文件需要同时成功，后续调度行为才会继续使用新值。
- 应用使用单实例互斥，避免多个进程同时操作同一份启动会话和回滚状态。

## 配置迁移事务

Profile、设备策略包和设置属于不同的持久化存储，导入不能依赖“每个文件自身写成功”来假设整体成功。迁移包应用前会为实际参与的存储捕获原始文件快照，随后才按 Profile、设备策略包、设置的顺序提交。

- 导入入口串行化，避免两个迁移任务交错覆盖配置。
- 任一存储写入失败或导入被取消时，使用不受调用方取消影响的令牌按逆序恢复所有已捕获存储。
- 快照恢复的是原始文件树，包含 Profile 历史和改名产生的旧文件，不只恢复当前反序列化对象。
- 恢复成功时抛出带有“已完整恢复”状态的导入错误；恢复失败时保留每个存储的失败信息，禁止伪报导入已回滚。
- 导入前的 JSON、Schema、安全规则和重复 ID 校验仍在快照与写入之前完成，格式错误不会触发任何本地写入。
- Profile 或机型策略包顶层 JSON 损坏、无权限或读取失败时必须记录 `ConfigurationLoadIssue`，不能仅返回空集合；配置恢复保护在这些问题修复并重新加载前不能解除。
- 快照恢复在删除 live 文件前检查取消；一旦开始恢复，就使用独立于调用方的令牌完成整棵文件树，避免取消导致配置目录只恢复一半。
- 快照存储拒绝文件/目录类型冲突和 reparse point（junction、symbolic link 等）；递归捕获与删除只处理经过路径校验的普通文件，避免越出配置根目录。
- Profile、机型策略包及其历史读取也只枚举存储根目录下经过校验的顶层 JSON；发现 reparse point 或路径类型冲突时停止读取并报告配置加载问题，不跟随外部目录。
- Profile 历史回滚在打开具体 revision 前会再次校验完整路径，避免历史目录在运行期间被替换为 reparse point 后把回滚读取重定向到配置根目录之外。
- 所有 `AtomicFile` 写入在创建临时文件前以及最终替换前都会校验目标文件和父级目录；设置、回滚状态、启动保护状态、SQLite 数据库和诊断包不会通过重解析点写入外部位置。
- SQLite 运行记录每次创建连接前都会重新校验数据库路径，防止运行期间路径被替换为 reparse point 或目录。
- Profile、机型策略包和设置存储会串行化读取、保存、导入、历史回滚和快照操作，同时锁定诊断问题列表，避免调度线程与编辑器并发访问造成状态误报或快照交错。
- 单独 Profile 导入也使用本地文件快照；批量导入中途失败或取消时，已经写入的前置 Profile 会被逆序恢复，不留下半批次配置。
- 单独 Profile 导入的源路径也必须通过普通文件和 reparse point 校验，目录或重解析路径会在读取前拒绝。
- 单独 Profile 导入只接受合法的 JSON 对象或数组；标量、`null` 和空对象不会被静默当成空导入成功。
- 社区 Profile 和社区机型策略包同样按不可信来源处理：导入后 Profile 默认保持禁用，策略包条目也不会保留默认启用状态，必须由用户审阅后手动启用。
- 社区机型策略包导入与迁移包共用串行事务入口；包内 Profile 或策略包写入任一步失败时，两个配置存储一起恢复。
- 迁移导入在捕获快照阶段也使用统一的导入异常边界；如果目标存储无法安全快照，导入不会开始写入，并向调用方报告未应用状态。
- 如果配置导入或单独配置保存的快照恢复不完整，应用会把它识别为未知配置状态，暂停自动调度并阻止恢复按钮绕过安全闸门。
- 配置恢复未完成时，应用会先尝试恢复当前系统调度会话；用户需要修复并重新加载配置，在设置页明确确认后，才应重新启用自动调度。
- 设置页的恢复确认不只检查 JSON 是否能加载，还会重新执行 Profile 库结构校验；重复 Profile ID、多个已启用全局默认 Profile 或其他阻止级问题存在时，恢复保护不能被解除。

## 进程优先级保护

优先级调整执行前必须经过统一安全策略。当前基座默认阻止：

- `RealTime` 优先级。
- Windows 系统伪进程。
- 随芯调自身进程。
- 已知 Windows 关键进程，例如 `csrss`、`lsass`、`services`、`wininit`、`winlogon`、`dwm` 等。

被安全策略阻止的动作应记录为不支持，而不是伪装成执行成功；动作结果必须提供稳定原因代码，用户说明不得依赖解析 Provider 技术消息。其余动作仍可安全应用时，控制台和运行历史必须明确显示“部分应用”及不支持的动作数量。
- 进程优先级和效率模式写入必须读回确认；确认失败时动作视为失败并保留回滚状态，不能只依据系统调用返回值报告成功。
- 进程映像路径通过 Windows 的映像查询接口读取，避免主模块尚未初始化时把 `ntdll.dll` 当作可执行文件。优先级读回前清除 .NET 进程对象缓存，避免把刚赋给属性的值当作系统确认结果。

## 供电状态变化与硬件电源急停门控（Power Emergency Gate）

当前供电状态由 `Win32PowerChangeWatcher` 默认每 150ms 轮询 `IPowerStatusProvider`，并交给 `IPowerEmergencyGate`。这是应用层轮询周期，没有 Windows 电源事件订阅或硬实时中断抢占保证。CPU 高级项仍是最大处理器状态百分比。

1. **瞬态急停触发语义**：
   - 当首次或持续观察到电池供电且尚未确认限频时，`PowerEmergencyGate` 请求 GPU 锁定在配置区间（默认 210–800MHz）。检测及写入时延、频率对应功耗和断电原因都需要实机证据；不承诺避免硬件关机。
   - 当检测到电源恢复交流电（Battery -> AC）时，门控自动调用 `TryResetLockedClocksAsync` 释放限频。
   - 门控串行执行供电补偿、GPU 自检完整锁频/复位及应用恢复，并在调用锁频前标记可能需要恢复；锁频返回 false 或取消后也不能丢弃恢复责任。复位失败可能已释放部分设备，不能继续声称全部卡已限频；随后观察到电池应重新限频。
   - 相同供电下的失败默认间隔 1 秒重试，供电变化立即处理；读取异常和独立取消不会终止守卫。未知供电保留限制，并阻止新 GPU 自检。

2. **安全网与生命周期兜底**：
   - **写前恢复意图**：AppRuntime 为 NVIDIA Provider 注入独立 `gpu-clock-recovery.json`。锁频前持久化，全部设备复位与标记清理成功后才清除；没有本应用记录时不调用 reset。该标记不是原 GPU 区间基线，见 [NVML 专题](nvidia-nvml-telemetry.md)。
   - **退出兜底**：正常退出检查 GPU 恢复结果；失败保留恢复记录和未正常关闭的会话。`ProcessExit` 只做尽力清理，强制终止或断电不能保证执行回调。
   - **启动恢复**：`FileStartupRecoveryManager` 不依赖脏会话标记存在才检查 GPU；返回 false 或异常时标记 `GpuRecoveryFailed` 并暂停调度，App 暂不启动供电轮询。取消立即向上传播。
   - **手动重试**：手动回滚同时尝试普通调度与 GPU 恢复。确认 GPU 恢复成功才能解除 GPU 保护；普通回滚成功不能清除 GPU 保护或配置修复要求。
   - **失败分界**：缺少 NVML 候选能力时不开始锁频，不创建新恢复标记。已尝试写入后的部分失败或设备恢复问题保留标记，不能一律视为无修改；损坏记录不覆盖、不删除。
   - **实机验证约束**：硬件急停效果、响应时延、复位与异常恢复需持续补充至 [硬件验证矩阵](hardware-validation-matrix.md)。

普通电源通知也没有应用级实时响应承诺，Event 41 且 BugcheckCode 为 0 不能单独证明电池欠压。依据：[Windows 电源状态通知](https://learn.microsoft.com/en-us/windows/win32/power/pbt-apmpowerstatuschange)、[Event 41 排查](https://learn.microsoft.com/en-us/troubleshoot/windows-client/performance/event-id-41-restart)。

GPU 自检会实际修改 GPU，只在已确认 AC 且没有待恢复状态时执行；检查期间供电转为电池或未知也应跳过写入。自检清理完成后才执行排队的供电动作，取消先清理再传播；急停模拟使用独立模型，不调用真实 GPU。当前已协调本应用入口，但仍未捕获第三方原锁频或写后对账，不能宣传为无条件无损。新增 GPU Profile 动作仍须满足下面的完整基线和对账要求。

## 扩展规则

后续新增电源、GPU 或后台限制动作时，必须沿用同一模式：

1. 在 Core 中增加清晰的 baseline、action plan 和 action result 模型。
2. 执行动作前捕获原始状态。
3. 同时记录预期应用状态，并用同一事务 ID 持久化回滚状态。
4. 恢复前比较 original / applied / current，避免覆盖外部修改。
5. Infrastructure 默认拒绝不安全目标。
6. 增加成功回滚、部分回滚失败、外部修改被保留、危险请求被阻止的测试。
